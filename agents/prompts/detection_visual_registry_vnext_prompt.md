# DETECTION V4 - VISUAL REGISTRY

Build the visual representation map and the locked commercial-object registry in one response. Keep these two levels separate. Inspect full pages and enlarged regions, map visible representations, resolve complete commercial packages from all relevant representations, then choose exactly one primary assembly anchor for each commercial object. Representation type, package membership and anchor eligibility are separate decisions.

## Visual representations

Each `visual_group` is one visibly distinct depiction that could help a later stage understand an in-scope fabricated product: overview, alternate perspective, elevation, section, detail, module, door leaf, panel, track, cabinet bay, schedule, or assembly fragment. It is not automatically a commercial object, quote line or quantity. A shared schedule, title block, layout or multi-object context belongs in `page_coverage`, not in an object boundary. `representation_kind` describes the image but does not decide whether it can be an assembly anchor.

Give each group a stable ordered `group_id`, physical `page_number`, short `location_hint`, literal visual `visual_description`, neutral `representation_kind`, and exactly one `commercial_role`. Keep descriptions terse. A group records only one visible depiction. Do not create a graph between groups.

`assembly_view` means a depiction shows enough of a whole finished assembly to anchor object identity. It is a candidate view, not a declaration of a new product. A primary orthographic elevation that establishes the overall finished envelope and one or more principal external dimensions is an `assembly_view`, including a regular grid of slats, shelves, bays or panels. It need not be a perspective or show every construction layer. `component_detail` means an isolated component, close-up, section, cutout, leaf, panel, track, module, hardware or construction fragment. `document_context` means a title block, sheet layout, schedule, legend or other document context. A component detail or document context can contribute evidence through `page_coverage`, but cannot be an assembly anchor or independently create an object. A complete separately depicted assembly remains an `assembly_view` even without OCR or a code.

Some enlarged regions are immediately followed by `LOCAL OCR FOR THE IMMEDIATELY PRECEDING REGION ONLY`. That text is geographically attached to that crop. Use it only as literal support for the depicted region, never as a boundary by itself. When classifying one depiction as a schedule, legend or other `document_context`, require table or legend semantics visible in that depiction or in its local OCR. Do not borrow column headings, revision data, title-block text, generic page OCR, or text from another enlarged crop. A dimensioned front elevation with repeated bays, slats, shelves or panels is not `document_context` merely because its geometry is grid-like.

## Commercial registry

Decide complete fabricated products a contractor would quote, fabricate, supply, install, replace or price independently. First resolve each product package from all its representations. Then give each object exactly one `primary_assembly_group_id`. It must name one `assembly_view` that shows the broadest finished product envelope, preferably a primary elevation or whole perspective with overall dimensions. A plan fragment, narrow dimension strip, section, close-up, isolated panel, or schedule can never be the primary anchor. Keep all alternate views, plans, details, renders and text that relate to that product in `page_coverage`; they remain full Estimation evidence even though they are not object anchors.

For every potential assembly, decide whether it is a new product or another projection of a product already represented. Do not create one object per assembly view by default. A change of projection can make the same item look unlike itself, so whole-silhouette similarity is not required. Resolve identity in this order:

1. Explicit document relation: the same code, callout, view reference, axis or label.
2. Matching construction topology: the order and count of bays, doors, supports, carcasses, frames, appliances, joints and other structural elements.
3. Dimensions that agree after a change of axes or depict compatible portions of one assembly.
4. Repeated unique geometric features: cut-outs, handles, posts, appliance locations, turning parts, mounting points, panel sequence or distinctive frame geometry.
5. Secondary signals only: same sheet, colour, material, visual proximity and room name. They may reinforce a relation already supported above, never establish it alone.

Use a literal printed object code, callout or label as the canonical `transport_label`. Different explicit object codes are affirmative separate-object evidence unless the document explicitly says they are alternate views of one code. Never replace an available literal code with `Object N`. A title block may carry an object code when its sheet designation identifies the fabricated assembly depicted on that sheet, especially when the sheet contains one finished assembly package. Distinguish that from project name, room name, revision data, job number, date, scale, or a generic sheet title, which are not object codes. When one sheet contains several assemblies, use a title-block code only with a visible callout or graphic association.

Test commercial separability, not visual adjacency. Different finished envelopes, principal functions or primary dimensions are affirmative evidence of separate commercial objects. A shared page, room title, project, palette, visual proximity, L-shaped placement, lack of codes, or generic furniture scope never proves a merge. A shared worktop, touching side panels or apparent continuous carcass is only candidate physical connection until the drawing shows why the parts are commercially inseparable. Without an explicit same-code, callout or view relation, treat two depictions as one product only when at least two independent identity signals agree, including matching topology, compatible dimensions after axis change, or repeated unique geometry. Direct physical contact cannot be the only reason to join them.

Account for every separately depicted complete assembly on overview, plan, elevation or render pages. Map it to one commercial object. Adjacent furniture with separate finished envelopes or functions remains separate even when it appears on every sheet, shares finishes, touches, or is presented together.

Different complete envelopes, functions, silhouettes or construction systems are strong independent-product evidence even without an object code. A vertical shelving unit, a track-supported door system and a long storage console separately drawn on one furniture sheet are three objects. Repeated projections remain one object each. Never absorb them into generic room furniture.

A kitchen, integrated cabinet wall or shelving wall is one object. Its blocks, modules, panels, fronts, carcasses, profiles, hardware and assembly sheets are construction detail, not objects. Several leaves on one continuous track are one Door system with quantity 1 unless the source establishes separate systems, tracks, deliveries or quote quantities.

`object_id` is ordered `object-001`, `object-002`, and so on. `transport_label` is an exact printed object code when present, otherwise `Object 1`, `Object 2`, and so on. `quantity` is complete physical units, defaulting to 1 when not explicit. `primary_assembly_group_id` is exactly one complete `assembly_view` owned by this object. The runtime derives its identity page directly from this anchor. A group has exactly one owner. Component details and document context remain unassigned. `visual_identity` states the complete physical product and its representations. `boundary_basis` records the factual reason this is one quote line and, when relevant, the concrete evidence linking alternate views to it.

## Evidence coverage

Evidence is the complete source context for the object, not a shortlist of pages that appear sufficient for a material calculation. For every physical upload page, return exactly one `page_coverage` entry. Put an object ID in `object_ids` whenever that page contains any visual, graphic, textual, layout, title, schedule, detail, plan, section, alternate view, assembly instruction or other source content that relates to that object. A page can belong to several objects. A render or picture is Evidence when it shows the object in another view. Do not omit a page merely because it lacks dimensions, material names, a crop-worthy region or an immediately calculable fact.

Use an empty `object_ids` only when the page contains no content related to any in-scope object. Give a brief factual `evidence_reason` for every page, including excluded pages. The runtime derives `estimation_evidence_pages` from this coverage, so it cannot silently discard an associated page. There is no arbitrary page-count cap.

Do not extract dimensions, materials, pricing or names. `boundary_basis` is the persisted decision audit: name the supporting visual groups or physical structure. If it connects separately depicted representations, state the specific positive relation, never a generic statement such as "one system" or "same sheet". Return schema JSON only.
