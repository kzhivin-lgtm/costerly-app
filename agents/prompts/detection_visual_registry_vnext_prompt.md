# DETECTION V4 - VISUAL REGISTRY

Build the visual representation map and the locked commercial-object registry in one response. First inspect the full pages and enlarged regions, determine document-wide measurement units, map visible representations, then decide the commercial objects. Keep these two levels separate in the output. Use the Pairwise merge-proof procedure before joining any two complete assembly views.

## Document measurement context

Return `document_measurement_context` once for the whole uploaded document: `unit` is exactly `mm`, `cm`, `m`, `mixed`, or `unknown`; `evidence_pages` names the pages that establish it; `basis` states the literal document-wide evidence. Read unit conventions across the document, not from one isolated numeral. A bare 345 can mean 345 cm when other pages establish centimetres. This context is solely an auditable aid for visual-role decisions. Do not return dimensions, dimension candidates, conversions, or measurements for any object.

## Visual representations

Each `visual_group` is one visibly distinct depiction that could help a later stage understand an in-scope fabricated product: overview, alternate perspective, elevation, section, detail, module, door leaf, panel, track, cabinet bay, schedule, or assembly fragment. It is not automatically a commercial object, quote line or quantity. A shared schedule, title block, layout or multi-object context may remain an unassigned navigation group; it belongs in `page_coverage`, not in several object boundary lists. Do not combine a location plan, a narrow plan projection and a frontal elevation into one visual group merely because they occur on one sheet.

Within this one response, use this order. First enumerate visually distinct islands from pixels only. OCR must not create, split, merge or extend an island. Then, before assigning a role to each already-enumerated island, read its spatially nearby OCR and sheet-level literal context. OCR may establish the caption, product code, dimension meaning or table semantics that resolves the island's role. Only then assign `assembly_view`, `component_detail` or `document_context`, and then decide commercial-object boundaries.

Give each group a stable ordered `group_id`, physical `page_number`, short `location_hint`, literal visual `visual_description`, neutral `representation_kind`, exactly one `commercial_role`, and concise factual `role_basis`. `role_basis` must name the observed visual feature and any OCR fact that establishes this role, and name the document unit only when it was actually used. Keep descriptions terse. A group records only that one visible depiction. Do not create a graph between groups: decide alternate views and product boundaries directly from the full visual evidence in the commercial registry.

Use exactly these role tests:

1. Exclude floor plans, reflected-ceiling plans, electrical, plumbing, HVAC/MEP and coordination plans. They are out of scope for Detection and Estimation. Do not create a visual group for them, even when they show a product location, tag, room name or broad external dimension. They receive an empty `page_coverage.object_ids` entry with an exclusion reason.
2. `assembly_view` means a depiction has a visibly bounded finished fabricated-product envelope and positive whole-product evidence: external overall axes that measure the product itself, an object code or caption, or a complete recognizable construction topology. It is a candidate view, not a declaration that it is a new or independent product. Only this role may appear in an object's `visual_group_ids`. A complete unlabelled product can qualify through its visible construction. A complete plan projection may qualify; a location plan does not.
3. A large unit-normalized dimension is supporting evidence only after a product envelope is visible. It never automatically promotes an isolated rectangle, room elevation, wall section, floor plan or partial fragment to `assembly_view`. Dimensions that describe the room, wall or reference layout are not product external axes.
4. A dense regular grid is not automatically a schedule or a component detail. Call it a schedule only when the same island has positive table semantics: a heading and labelled rows or columns, line-item labels with per-cell values, or another explicit tabular structure, and no single finished-product envelope. Repeated lines or cells alone never prove a schedule. When a bounded outline, overall product axes and a nearby or sheet-level code/caption or finished topology show a shelving wall, display rack, decorative lattice, screen, room divider or panel, treat its full elevation as an `assembly_view`; the repeated bays, shelves and dividers are its internal topology.
5. `component_detail` means a positively partial depiction: an isolated component, close-up, cutaway, section, leaf, panel, track, module, hardware or construction fragment. It is evidence for the relevant assembly through `page_coverage`, but can never itself create a commercial object or appear in `visual_group_ids`.
6. `document_context` means a title block, sheet layout, schedule, legend or other document context. It cannot create an object or appear in `visual_group_ids`.

A visually isolated region is not automatically an `assembly_view`: use that role only when it clears the positive whole-product test. Conversely, a complete separately depicted assembly remains an `assembly_view` even without OCR or a code.

## Commercial registry

Decide complete fabricated products a contractor would quote, fabricate, supply, install, replace or price independently. Start only from `assembly_view` groups. A `component_detail` never becomes a commercial object merely because it appears separately. It remains supporting evidence on its page for the parent assembly. A `document_context` never becomes an object.

Before creating any object, resolve identity across all `assembly_view` groups. For every assembly view, decide whether it is a new product or another projection of a product already represented. Do not create one object per `assembly_view` by default. A change of projection may make the same item look unlike itself, so whole-silhouette similarity is not required. Resolve the relation using the following evidence, in priority order:

1. Explicit document relation: the same code, callout, view reference, axis or label.
2. Matching construction topology: the order and count of bays, doors, supports, carcasses, frames, appliances, joints and other structural elements.
3. Dimensions that agree after a change of axes or depict compatible portions of one assembly.
4. Repeated unique geometric features: cut-outs, handles, posts, appliance locations, turning parts, mounting points, panel sequence or distinctive frame geometry.
5. Secondary supporting signals only: being on one sheet, colour, material, visual proximity and room name. These may reinforce a relation already supported above, but never establish it alone.

When the evidence establishes the same product, put every corresponding `assembly_view` in one object's `visual_group_ids` and state the cross-view evidence in `boundary_basis`. When positive identity evidence is absent, do not invent a merge solely because the views look stylistically related.

## Pairwise merge-proof procedure

Start from separate commercial assemblies. Before grouping two `assembly_view` groups under one owner, apply this comparison to that pair. Different finished envelopes, principal functions, or primary dimensions are affirmative evidence of separate commercial objects. A pair can merge only when the source overcomes that evidence.

Test commercial separability, not merely visual adjacency. Ask whether each finished assembly could reasonably be fabricated, transported, installed, replaced, or priced separately. A shared page, room title, project, material palette, visual proximity, L-shaped placement, lack of object codes, or generic furniture scope never proves a merge. A shared worktop, touching side panels, or an apparent continuous carcass is only a candidate physical connection. It does not prove one commercial object unless the drawing also shows why the two parts are commercially inseparable.

An explicit same code, callout, or view reference can prove identity on its own. Without one, a merge needs at least two independent evidence types and at least one identity-level comparison: matching construction topology, dimensions that agree after a change of axes, or repeated unique geometry. Direct shared structure may support a merge but cannot be its only evidence. Never infer a shared carcass or continuous construction from adjacency, an L-shaped layout, or matching finishes.

A recognized kitchen, integrated cabinet wall, shelving wall, or one continuous door-track system may remain one commercial object when the visual evidence establishes one integrated joinery envelope. Its modules, appliances, panels, fronts, and details are not separate objects. A worktop alone must not absorb adjacent non-kitchen furniture into that object.

`merge_proofs` is a compact flat audit, not a second analysis stage or an all-pairs graph. For every object with N `visual_group_ids`, return exactly N-1 proofs which connect those views. Return no proof for a one-view object. Each proof contains its two group IDs, source pages, a concrete observed fact, controlled `evidence_types`, and the observed reason the parts are commercially inseparable. The group IDs may be linked in any order. Do not use generic statements such as "one system", "same room", or "continuous L-shape" as the observed fact or inseparability reason.

Before creating the registry, account for every separately depicted complete assembly on overview, plan, elevation or render pages. Map it to one commercial object, or merge it only after its pairwise proof clears the commercial-separability test. Adjacent furniture with separate finished envelopes and different functions remains separate even when it appears on every sheet, shares finishes, touches, or is presented together. A one-object `boundary_basis` that covers several complete assemblies must state the proof-backed integration, never merely call them an integrated system.

Different complete envelopes, functions, silhouettes or construction systems are strong independent-product evidence even without an object code. A vertical shelving unit, a track-supported door system and a long storage console separately drawn on one furniture sheet are three objects. Repeated projections remain one object each. Never absorb them into a generic room-furniture assembly.

A kitchen, integrated cabinet wall or shelving wall is one object. Its blocks, modules, panels, fronts, carcasses, profiles, hardware and assembly sheets are construction detail, not objects. Several leaves on one continuous track are one Door system with quantity 1 unless the source establishes separate systems, tracks, deliveries or quote quantities.

`object_id` is ordered `object-001`, `object-002`, and so on. `transport_label` is an exact printed object code when present, otherwise `Object 1`, `Object 2`, and so on. `quantity` is complete physical units, defaulting to 1 when not explicit. `identity_pages` uses physical upload page numbers. `visual_group_ids` lists only `assembly_view` groups that prove this object's commercial boundary. A group has exactly one commercial-object owner and must never appear in more than one object's `visual_group_ids`. A `component_detail` or `document_context` must remain unassigned. If a shared page, schedule, title block or layout relates to several objects, assign every relevant object through `page_coverage` while leaving that context group unassigned. When one sheet visibly contains several complete assemblies, map them as separate `assembly_view` groups before assigning ownership. `visual_identity` states the complete physical product and its views, not one preferred image. `boundary_basis` records the factual reason this is one quote line. `merge_proofs` is always present, including as an empty list when every object has one assembly view.

## Evidence coverage

Evidence is the complete source context for the object, not a shortlist of pages that appear sufficient for a material calculation. For every physical upload page, return exactly one `page_coverage` entry. Except for the explicitly excluded plan types above, put an object ID in `object_ids` whenever that page contains any visual, graphic, textual, layout, title, schedule, detail, plan, section, alternate view, assembly instruction or other source content that relates to that object. A page can belong to several objects. A render or picture is Evidence when it shows the object in another view. Do not omit a page merely because it lacks dimensions, material names, a crop-worthy region or an immediately calculable fact.

Use an empty `object_ids` only when the page contains no content related to any in-scope object, or when it is an excluded floor, reflected-ceiling, electrical, plumbing, HVAC/MEP or coordination plan. Give a brief factual `evidence_reason` for every page, including exclusions. The runtime derives `estimation_evidence_pages` from this coverage, so it cannot silently discard an associated page. There is no arbitrary page-count cap.

Do not extract dimensions, materials, pricing or names. `boundary_basis` is the persisted decision audit: name the supporting visual groups or physical structure. If it merges separately depicted assemblies, state the specific positive integration that makes them one product. Never use a generic statement such as "one system" or "same sheet". Return schema JSON only.
