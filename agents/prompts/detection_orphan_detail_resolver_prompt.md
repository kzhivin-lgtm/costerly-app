# DETECTION V4 - ORPHAN DETAIL RESOLVER

This is a conditional, narrowly scoped repair stage. The normal Visual Registry has already completed. Do not recreate the visual map, reconsider valid object boundaries, rename objects, or alter a valid object's quantity, identity pages, group ownership, or merge proofs.

You receive `candidate_groups`, the unowned `component_detail` groups that triggered this repair, plus `page_scope_groups`, every visual group on the same unresolved physical page. The primary role on a page-scope group is provisional for this repair: it may be a product depiction despite being labelled `document_context`. `eligible_assembly_group_ids` is the only set from which a promotion may select views. Already-owned views remain locked and cannot be selected.

`existing_objects` are the only locked commercial objects. Only an ID from `existing_objects` may appear as `target_object_id`. `provisional_candidates` are identity hints from incomplete Registry records, not objects and not attachment targets. They have no ID by design and will be replaced or discarded after this repair. If their candidate views establish an independent commercial product, use `promote_to_new_object`, never an attachment to a provisional candidate.

Resolve every candidate group exactly once. Inspect the complete page scope before deciding: a top plan/context view, profile, and elevation can be complementary views of one product even where the first Registry labelled some of them `document_context`. A true title block, revision table, legend, schedule, or isolated material note is context, not a view.

For each candidate cluster choose exactly one decision:

1. `attach_to_existing_object`: the candidates are supporting construction evidence for one existing locked object. Use that exact ID from `existing_objects` as `target_object_id`. This does not add a view to that object's `visual_group_ids`. Set `assembly_group_ids` and `merge_proofs` to `[]`. `attachment_evidence` is mandatory and must identify a visible direct cross-reference, callout, or view link on the candidate page. An inference from similar codes, shared dimensions, similar finish, drawing sequence, or visual style is not attachment evidence. If the provisional candidate has its own different printed code and no visible direct link to the target, attachment is forbidden: promote it or classify it as non-commercial support.
2. `promote_to_new_object`: the candidates together depict a complete independently fabricable, supplied, installed, replaced, or priced product. Supply its object fields. `assembly_group_ids` must include every eligible page-scope group that visibly depicts that promoted product, including every candidate group, and no title-block or schedule context. Every selected group becomes an `assembly_view`. When it has N groups, provide exactly N-1 compact pairwise proofs connecting them. In every proof, use `primary_evidence_type` and `secondary_evidence_type`: direct document relation permits secondary `not_required`; otherwise provide two distinct actual evidence types.
3. `non_commercial_support`: the source positively establishes that the candidates are not an independently quoteable product and do not belong to any existing commercial object. Use only for a material/profile/detail/legend or other non-commercial support item. Do not use it merely because the association is difficult. Set `assembly_group_ids`, `merge_proofs`, and `attachment_evidence` to `[]`.

Use evidence in this order: explicit cross-reference, callout, or view linkage; matching construction topology; dimensions compatible after a change of axes; and unique repeated geometry. Colour, material, sheet proximity, or room name can only support stronger evidence. Different finished envelopes, functions, or incompatible principal dimensions are positive evidence of a separate product.

A different printed code is a distinct document identifier. Shared characters, a numeric root or suffix, drawing sequence, visual style, or a coincidental dimension never proves that it belongs to another code. Attach only where the document directly links the candidate to the target object. An own code with several coherent orthogonal or dimensioned views and no direct relation to an existing object is strong independent-product evidence. A set of details with no owner is not automatically a product, but it must receive a deliberate decision. Never leave a candidate group unresolved.
